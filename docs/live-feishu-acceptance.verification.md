## 隔离与入口

1.52.0 的同一机器人 profile 只能绑定一个需求项目，且群路由必须与该项目相同。现有群无法选择一个话题使用独立资源。新增回归先复现拒绝，再为同一既有消费者增加精确的群、根消息、需求链接绑定。默认群项目及权限保持原样。子项目继承既有身份边界，Runner 启动模型前核对项目摘要、资源配置摘要和源码根。

隔离归档和审批各使用独立 Git 根、回环 HTTP 服务、专用 MySQL schema 与限制到本库的账号、独立浏览器上下文及报告路径。实际验证跨库查询拒绝、未登记资源写入拒绝、不同话题或文档不能进入隔离路由。需求读取、用例发布、消息回读和文件下载使用同一已授权飞书文档身份，群消息仍由原专员消费。

## 实际缺陷与回归

| 现象 | 根因 | 回归依据 |
| --- | --- | --- |
| 1.52.0 无法在现有真实群同时保有普通项目和独立隔离话题 | 路由把 profile 与群限制为单一项目 | 改前失败，改后验证同一消费者、精确话题和需求绑定、身份校验、去重及 Runner 拒绝越界 |
| 1.53.0 的一次通知状态提交返回 Windows `EPERM` | 状态文件被暂时禁止替换时，单次原子 rename 直接失败 | 独立 Windows 进程持有读取句柄，旧版同错误；新版释放后原子提交，事务只运行一次，旧文件在此前保持完整 |
| 1.53.0 的真实卡片只显示通用工具计数，遗漏 Runner 统计，清理报告沿用通用完成标题 | 文本状态与卡片采用不同展示，通用 `activity.total` 在需求测试中也可表示用例数量 | 原话题回读保存修复前正文和同轮结构化进度。新版复用统计，并区分产品失败、业务未完成和取消后仅清理报告 |
| 归档首轮清理后有回读但过程审查缺动作回执 | native 清理直接丢弃 `scope.restore` 的实际返回值 | 真实回环 HTTP 回归先复现。修复后动作回执按变更键和时间持久化并进报告索引，进程断开导致的丢回执通过状态对账收尾，确认零重放、无伪造回执。审查标记当前尝试和测量轮次，旧历史保持归属 |
| 审批反例恢复后实测回到原状态，台账仍未决，旧版继续执行了更早的撤销 | 恢复后套用正向异步就绪标记；清理在失败后继续向前撤销 | 用真实回环 HTTP 复现。新版恢复后比较原快照，仍未决即暂停更早撤销。历史对账需匹配原恢复响应、同对象后续实际回读、时间顺序和当前最终状态，拒绝跨任务或早于动作的证据 |

窗口期发现的旧测试时序依赖采用显式回执与阶段断言修正。重复无进展仍按缺口调查，未改变模型、独立预期、冻结基线、页面证据或清理契约。
