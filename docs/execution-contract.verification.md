# 执行契约与页面取证验证

AgentOS 1.58.0 基于 1.57.0 继续使用原测量、变更台账和 15 表报告契约。验证分别记录确定性回归、真实组件、正常 Runner 和群入口。具体项目的话题 ID、夹具地址、实例配置和运行记录保存在部署方私有证据目录。

| 证据类别 | 修改前 | 回归判据 |
| --- | --- | --- |
| 计划与审查 | 审查要求填派生的 `baselines`、过程 `measurement` 和阶段 `ready`。相应参数被拒绝。登记的只读入口也可能从审核材料中缺失。 | 审查收到可提交 Schema 和已登记入口。工具明确提示派生字段及合法替代。检查项和准备过程分开表达。可修正尚未冻结的计划片段。非法的过程动作、路由和回执合同在冻结前被拒绝。 |
| 过程基线 | 测量需要说明准备后的完整状态，缺少直接绑定相应写动作的过程契约。候选执行中已证明集合基线，但变更审查只收到单对象回查和独立服务审计预检。 | 真实 HTTP 计数服务在过程证据缺失、来自冻结前或渠道不匹配时保持零场景写入。冻结后、准备后采集独立观测。变更审查收到已证明的具体字段、范围和时点。旧基线不得被事后重查替换。 |
| 页面对象 | 分别拼接的业务键和标题无法证明配对。归档前不可见的目标行无法用实际目标 DOM 验证读取方法。 | 真实 Chromium 读取可见的同一行，按完整键定位。重复标题、相似键、乱序、分隔符、空集合和加载等待纳入回归。重复键和普通聚合串继续拒绝。方法样本不替代场景目标，实际断言仍须采用相同布局、选择器及字段。 |
| 调用范围 | 对有限入口的检查可能只核对列出的写接口。重建测量时旧记录已保留，白名单校验仍可能漏掉旧轮次。 | Runner 实际发送记录覆盖 HTTP、浏览器与数据库连接。阶段范围内逐条检查，包含重建前的请求。未授权调用、未决传输和无法补证的旧日志版本不证明合规。拒绝后续违规发送时，必要恢复不被锁死。 |
| 外部回收 | Runner 的清理、业务比较和准备者的回收相互依赖，可能无法收尾。 | 分别保存业务比较、Runner 恢复、报告及外部回收。回执按责任人、对象、来源和时点核验。Job 结束后才能取得的外部回执保留独立待办。 |

可单独运行 `node --test test/requirement-execution-contract.test.js`。其中浏览器、HTTP 端点和 Runner 传输是真实本机组件。测试中的模型和语义审查是可控夹具，另用冻结源码上的正常 Runner 验证模型能否自主发现和完成。

`runnerScope.phase=all` 覆盖该用例本次尝试的准备、场景和 Runner 恢复，包含该尝试中的全部测量轮次。它不表示其他用例或其他调用者的所有请求。外部回收须有实际来源和证明，工作簿可以保留待办，已投递的工作簿不会因 Job 结束后收到回执而自动改写。

## 源码交付检查

冻结运行源码包含 143 份文件，SHA-256 为 `8cfa72903f00dc343d810a84eb86105fe0ec71e5ea6003ba0a62f2d1c8ad1471`。Windows Node 22.23.2 上完整检查 827 项全部通过，比 1.57.0 基线增加四项。工作台 14 项全部通过。两组检查均无失败、取消或跳过。已接入回环 MySQL、两份需求测试 Skill 和真实工作簿夹具。

同一冻结源码以 `gpt-5.6-sol/high` 正常 Runner、模拟飞书传输运行运价留出。实际完成一条用例、四项独立业务检查和两项过程核验。五次 HTTP 请求均为只读，零业务写入和未决变更。15 表工作簿已用独立读取器核对数据计数与摘要。模型自主执行，夹具未预填执行计划或判定。归档场景也已通过四项业务比较，并记录与归档动作关联的完整集合基线。模拟传输的结果与实际群验收分别记账。

归档的本机模型任务最终为一条通过、四项业务检查和两项过程检查，四次隔离写入均回查恢复。发运对照保留了不在封闭白名单内的实际根路径请求，重建测量未消除历史证据。两个用例仍为未执行。报告单列外部回收待办。外部夹具所有者在 Job 结束后另行清理并保存回执，原报告保留当时状态。

## 部署实例与真实群验证

仅部署 LTX 专员。运行源码 SHA-256 与上述冻结一致。首次切换在启动刷新历史卡片的待投递阶段触发回滚。第二次使用独立备份，等待回执结清后完成实际加载检查。原任务、历史用例和清理台账均按字节或对象摘要对比。其他专员程序和实例配置保持原状。

| 隔离场景 | 真实群结果 | 实际请求和恢复 |
| --- | --- | --- |
| 归档正例 | 一条通过。六项业务比较、三项过程核验，包含动作前集合和真实 DOM 完整键。两条不同的同话题发起消息只关联一个 Job，第二条返回原 Job 状态。 | 24 次请求，其中四次写入含准备、业务动作和恢复。两笔台账全部回查，零残留。 |
| 发货修订号负例 | 一条产品失败。三项业务比较中两项通过，实际版本为 2，独立预期为 3。 | 四次只读请求，零变更。 |
| 库位容量重试 | 首次落盘为一条阻断。解除回环夹具拒绝条件后，原话题的「重试阻断」使同一 Job 的第 2 次尝试通过。用例表、原尝试和原附件可回读。 | Runner 两次只读查询。工程侧另做一次回环 403 探测，随后切换夹具。零变更。 |

三份用例表均从真实飞书回读。四份实际群附件分别下载，逐份核对字节摘要、15 表内容、结果卡和对应台账。未注入人工计划、预期或结果。两个 Agent 模式场景分别保存四次和六次工具诊断，均未重建测量。库位场景使用既有静态目录适配器。最初的阻断报告保留依赖名及阻断类别，HTTP 状态由独立夹具回执佐证。

真实群的消息去重证据来自两条不同消息。相同事件重放由工程回归覆盖。隔离验收只访问回环资源。真实 SIT 的认证构建及生效日志脱敏、主库有效只读库范围和库存库完整连接条件仍受原门控保护。发运场景若要证明每次调用的查询参数归属，还需能关联 Runner 与外部审计的逐请求证据。
