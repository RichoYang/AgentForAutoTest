# 需求执行链路：测量、证据与恢复

适用能力起点：AgentOS 1.50.0。1.52.0的冻结前预检、业务/过程分类及页面阶段补充见[执行前契约](execution-preflight.md)。设计与证据分类见 [修复范围](execution-chain-repair.spec.md)。这些能力用于授权的隔离验收及项目测试，不能把历史任务、报告或知识条目当作新业务执行授权。

## 正常执行

1. 使用 `test_source` 调查当前源码，用 `test_schema` 读取真实结构，登记动态业务操作。工具发布的 JSON Schema 与参数校验共用定义；业务请求体和输入保持动态发现。
2. `test_mutate purpose:prepare` 准备可归属、可恢复的样本。恢复快照记录准备前状态；它不等于后续场景的不变性基线。
3. 准备全部完成后重新读取对象、身份与基线，`test_plan` 固定原用例的独立预期。一个复合预期可以拆分多个检查；不得用实际结果改预期。
4. `test_measure` 验证取值方法、主体、完整性和比较口径；放在计划检查`measurement`中的预检自1.52.0起在发布冻结计划前完成，失败候选可修正。此步骤只核验测量契约，不计为业务通过。场景写入要求全部检查预检完成；已经冻结的预期仍不可随实际结果改变。
5. `test_mutate purpose:scenario` 执行场景。实际观测必须来自相应渠道；页面检查使用真实 DOM、截图和业务就绪信号，不能用截获的 API 数值替代页面值，也不能等待目标金额出现来隐藏错误。
6. `test_assert` 按程序计算和冻结预期比较；`test_finish` 保存结论，Runner 按台账逆序恢复并回查，再生成固定 15 表报告。缺检查不会算整条通过。

所有字段路径相对于工具回执的 `data`。HTTP 路径如 `["body","order","id"]`，数据库如 `["rows",0,"id"]`；不得再加 `data`，也不能省略 `body`。写入前检查恢复测量路径；未知字段、空值和空集合是不同证据。

预期中的调查、原值保留、回执对账、就绪和恢复要求映射到 `processChecks`，由 `test_process` 使用现有真实台账与指定观测核验。`kind` 为 `execution_evidence`、`receipt_reconciliation`、`readiness` 或 `cleanup`；可用 `relatedCheckIds` 关联独立业务检查。它们有独立覆盖统计，不能替代金额、状态、数量的程序比较，也不需要编造业务布尔字段。过程证明之后若有新的业务变更，完成校验会要求重新核验。清理过程先执行 `test_cleanup` 并回查；报告在此后另行构建验证。

测量预检可复用同一方法的前置样本，不主张未来时点已经执行。即将创建的子记录尚不存在时，实际父对象/范围、源码响应构造和 schema 可以证明未来取值路径；实际断言仍须回读子记录及其关联，不能借此跳过数据身份或页面证据。计划支持 `type:"null"`、`expected:null`、`operator:"equals"`；真实空值、缺失和零分别判断。

## 全记录与集合快照

`test_snapshot` 接收授权数据库资源、库、表、明确的等值 `scope`，以及可选 `fields`、`pageSize`。默认包括 schema 的所有列，要求实际主键及范围字段全部在覆盖中。范围须包含当前业务需要的租户、对象和期间，审核仍会检查业务范围是否正确。

采集使用同一 InnoDB 只读可重复读事务，独立计数、按主键稳定分页并证明末页耗尽，检查字段、主键唯一性、行数及 schema。页大小影响传输，不是总行数上限。BIGINT、DECIMAL、日期和微秒按连接器原始文本保留；空集合有零行证明及稳定摘要。行值、字段摘要和采集起止时间完整落盘；模型按需分页读取。

TIMESTAMP统一以UTC采集及筛选，并在契约记录时区；DATE/DATETIME保留数据库中的日历值。默认会话时区变化不能制造业务差异，业务字段的原始日历时区仍由项目知识说明。

快照不变性检查使用原始快照 `hash` 作为独立预期和 `basis`，在动作后按相同范围及覆盖再次采集。程序同时保留增行、删行、改字段及前后值；不能仅凭两个临时聚合 SQL 的短摘要判断完整性。分页大小改变不改变测量契约；真实范围、字段或 schema 改变须重新核验。

当前内置快照连接器支持 MySQL InnoDB 单表。其他存储或跨表业务一致性须有相应事务/不可变版本证据；普通 API 分页和跨表 SQL 不能自动获得这一证明。

## 冻结基线与测量修正

冻结的是业务预期和原基线的来源时点。可用 `evidenceRefs` 引用同次尝试保存的原始观测字段，补充完整性、来源、资源和时点；`constraints` 由程序核对实际字段值。补证不得用操作后查询证明操作前完整性。审查明确给出已证明、缺证据、证据矛盾或契约不合法，以及具体字段和修正方向。

审查同时接收 Runner 从原基线提取的采集时点、准备完成时点、场景开始时点及预检回执。程序已证明的时间先后无需模型另查业务重建；范围、字段语义与完整性仍要核验。

不能证明原基线时，调用 `test_measure {action:"restart",reason:"具体缺口"}`。Runner 先完成当前范围的恢复回查；有未决副作用时拒绝重建。成功后保存原计划、原断言、原观测、旧别名及清理证据，开启新的测量时期，重新准备、采集和执行。旧观测仍可读，但不能再绑定新基线或断言。仅修正未比较检查的主体时可用计划的 `identityCorrections`；该检查的旧预检同时失效。

`nullAs` 只将真实 `null` 按已审查业务规则转换，必须引用源码并保留原值、规则、计算操作数、实际观测时点及来源。缺失路径、空字符串、未知值、HTTP 错误和显式失败响应不会默认补零。页面缺字段不能靠计算代替实际显示。

## 恢复与知识

变更意图在发送前持久保存。相同变更 ID 重试先按原契约对账；已生效不再发送，状态不明确则保留台账和具体缺口。恢复仍按原业务目标、恢复操作、身份和资源回查。只有清理回查完成，后续独立用例才可继续。

异步操作在 `verify.ready` 提供实际结束信号，例如 `{field:["body","order","state"],operator:"not_equals",value:"PROCESSING"}`。独立源码审查须证明该信号覆盖后台副作用且接受失败终态，不能只等待目标金额或成功状态。Runner 在写后、对账及恢复前轮询同一只读操作，记录时间、实际值和就绪结论；单次等待默认30秒，可用`timeoutMs`设置。超时保持未决，不提前恢复，也不增加整个任务的耗时上限。

`test_evidence {evidenceRef:"agent-...json"}` 可回读工具返回的本Job清理、变更及审查回执；这些审计材料标为`kind:audit`、`usableForCurrentAssertion:false`，不能当业务观测 ID 或原始基线。路径及文件中的Job/项目归属由程序核验。

旧版本可能把错误字段路径取到的缺失值误作相等。新版不信任这种清理回执。仅在已保存原始 HTTP 响应能唯一证明遗漏了 `body` 封套时，独立审查可以补全该路径，另存原契约、旧清理和修正证据；不会修改业务参数、业务预期或恢复操作。其他无法证明的旧测量保持未决，需提供准确原始证据。显式 `cleanupOnly` 可使用修复执行器处理原保存的恢复契约，并记录执行器版本；不重试用例，原资源身份仍须相同。

项目知识只保存源码证实的入口模板、结构和调查位置，以及来源哈希、资源、schema、身份边界和失效条件。操作复用重新核对边界；实时对象 ID、余额、状态和基线每次读取。既有知识文件无需配置迁移；缺少审核边界的旧操作需要重新登记。

取消任务在 Runner 入口保持终态。升级不会自动领取、重试或重算已取消 Job；显式仅恢复入口与业务重试分开。

## 进展与排查

进度区分用例完成及五类结果、当前用例的独立检查覆盖、每个检查的历史尝试与当前结论、执行器错误、未决变更、清理、阶段、时长和下一步。历史失败不因后来同检查通过而消失；重复断言不增加独立覆盖数。

同一工具目标持续出现相同缺口且没有相关新证据时，保存已确认事实、缺失字段和替代调查路线，停止重复空转。改写回答、SQL或增加无关观测不等于解决缺口。没有新增整个任务的固定时长、轮数或调用次数上限。

诊断候选、字段错误、独立审核、修正及工具事件存入 Job 私有诊断归档；报告引用脱敏证据。先检查字段根路径、原始时点、主体、schema及清理回执，再决定补证、恢复重测或解除外部依赖。报告生成、清理完成和业务测试完成分别判断。

过程审核不重复判定业务结果：产品失败可以与取证正确、就绪条件满足、清理完成同时成立。审核收到实际已比较检查的引用；字段语义审核收到同一观测的已测字段和真实页面身份时序。它们用于证明范围和关联，不能用别行、别时点或兄弟检查的通过替代当前检查。

页面测量核验展示位的职责，不要求产品实现已正确从API字段赋值。当前对象状态位硬编码了错误状态时，保留真实DOM和源码证据，由独立预期判失败；不能要求先修产品才能执行测试。字段名相似、无关区域和其他对象仍不能证明对应职责。后续调用未另传`sourceRefs`时沿用冻结测量已有引用，并继续核验源码文件和资源边界。


## 报告原生组件生命周期

报告继续使用已固定的Skill、15表契约、布局与统计条件。布局和实际XLSX文件回查分别在新Node进程中调用原生组件，避免保留上下文二次导入挂起；没有新增配置或任务总时限。回查核对用例ID、五类统计、变更及清理台账ID，并将实际读取文件SHA与登记产物匹配。报告检查点恢复不重跑已完成业务，业务完成、清理完成与报告完成分别记录。

诊断见report-build-error.json及report-count-verification.json。原生组件内部问题尚未修复；当前通过进程生命周期隔离避开。若改变这层隔离，须重新完成同一样本及连续构建回归。
